# 「AIオフィス」のつくり方 — AIを相談相手ではなく、仕事仲間にする運用ガイド

作成日: 2026-08-27
作成者: 押久保オフィス（writer担当）
用途: 自分のAIオフィス運用を他の人に伝える・マネしてもらうための説明資料

---

## 1. ひとことで言うと何か

**「フォルダひとつを"自分の会社（オフィス）"に見立てて、Claude Codeをその会社の社員として働かせる」** 仕組みです。

多くの人はAIを「毎回ゼロから質問するチャット相手」として使っています。この方式の問題は、会話が終わるたびに文脈が消え、毎回同じ説明を繰り返すことです。

AIオフィス方式では、次の3つをぜんぶ**ファイルとして残す**ことで解決します。

1. **会社のルール**（何の仕事をする組織か、判断基準は何か）
2. **社員の役割と記憶**（誰が何を担当し、何を学んだか）
3. **仕事の記録**（今何が進行中で、何が終わったか）

AIは起動するたびにこれらのファイルを読むので、「昨日までの続き」から仕事を始められます。つまり、**AIに会話を覚えさせるのではなく、会社の仕組み側に記憶を持たせる**のがポイントです。

---

## 2. 仕組みの3本柱

### 柱1: 憲法ファイル（CLAUDE.md）— 会社の定款

オフィスのルート直下に `CLAUDE.md` という1枚のファイルを置きます。Claude Codeはこのファイルを毎回自動で読むため、ここが**オフィスの憲法**になります。

書く内容:

- **このオフィスは何の仕事をする場所か**（ドメイン定義）
  - 例: 「ドメイン1: 部門経営業務（メイン）」「ドメイン2: メディア編集長業務」のように業務領域を分け、タスクを受けたらどちらの業務かを意識させる
- **数値目標・行動指針**
  - 例: 「売上◯億・粗利率◯%」「評論家ではなく、実践者であれ」
- **タスクを受けたときの標準動作**
  - 例: 「①担当エージェントを選ぶ → ②チケットを作る → ③作業開始」
- **禁止事項（ガバナンス）**
  - 例: 「データ・成果の捏造禁止」「部分完了を完了として報告しない」

**コツ: 「AIへの指示」ではなく「新入社員に渡すオンボーディング資料」のつもりで書く。** 会社の目的・組織図・仕事の受け方・やってはいけないことが1枚で分かる状態にします。

### 柱2: エージェント（社員）— 役割別のペルソナと記憶

仕事を役割ごとに分け、それぞれを「社員」として定義します。

```
agents/
  writer/          ← ライター（執筆担当）
    CLAUDE.md      ← 職務記述書（役割・行動ルール・禁止事項）
    memory/
      raw.md       ← 日報（作業のたびに追記する生ログ）
      fact.md      ← 確定事項（検証済みの事実だけを昇格）
      digest.md    ← 要約（すぐ引ける知識のまとめ）
  analyst/         ← データ分析担当
  editor/          ← 編集・校閲担当
  designer/        ← デザイナー
  ...
```

**職務記述書（各エージェントのCLAUDE.md）に書くこと:**

- 役割と責務（誰のために・何のために働くか）
- 行動ルール（例: ライターなら「結論を先に書く」「1文60字以内」「根拠のない断言をしない」）
- 他の社員との連携ルール（例: 「公開前は必ずeditorのチェックを通す」）
- やってはいけないこと

**3層メモリの運用ルール:**

| ファイル | 役割 | 例え |
|---|---|---|
| `raw.md` | 作業ごとの生ログを追記 | 日報 |
| `fact.md` | 検証済みの事実だけを昇格 | 社内ナレッジ |
| `digest.md` | 要約して即引ける形に | 引き継ぎ資料 |

作業のたびに raw に書き、確定したものを fact へ、定期的に digest へ再要約する。この流れがあると、**社員が仕事をするほど賢くなっていきます。**

### 柱3: チケット — 仕事の見える化

すべての仕事をチケット（1タスク＝1ファイル）で管理します。

```
workplace/tickets/
  unstarted/     ← 未着手
  in_progress/   ← 作業中
  pending/       ← 待ち・ブロック中
  completed/     ← 完了
```

- ファイル名は `YYYY-MM-DD_タスク名.md`
- 作成時に「ID・優先度・担当者・概要」を書く
- ステータスが変わったらフォルダを移動する
- 完了時に「実施内容・成果物・学び（`[INSIGHT]`付き）」を書き残す

これにより、**「AIが今なにをやっているか」「過去に何をしたか」が人間にもAIにも一目で分かる**状態になります。完了チケットの`[INSIGHT]`は、次に似た仕事をするときの再利用資産になります。

## 3. 3本柱を支える補助の仕組み

### 判断軸ファイル（本人の分身）

オフィス直下に自分の名前のファイル（例: `押久保.md`）を置き、**自分の思考・判断基準・回答の好み**を書いておきます。

- 例: 「結論先出しで報告してほしい」「経営判断は収益性・持続性・確実性の3視点で見る」
- 経営判断や資料レビューのタスクでは、AIに必ずこのファイルを読ませてから着手させる
- **「育てる」運用にする**: 判断ミスや学びが出たら「反省・失敗パターン」の節に追記する

これがあると、AIの提案が「一般論」ではなく「自分ならこう判断する」に近づきます。

### git（作業履歴のタイムマシン）— ビジネス職向け補足

このガイドには「git管理」という言葉が何度か出てきます。エンジニア以外には馴染みが薄い道具なので、ここで補足します。

**そもそもgitとは何か。**
フォルダ全体の「変更履歴」を記録する仕組みです。もともとはエンジニアがプログラムの管理に使う道具ですが、実態はシンプルで、**「フォルダ全体のセーブポイントを、好きなタイミングで何個でも作れるタイムマシン」**です。Wordの「変更履歴」機能の、フォルダまるごと版だと思えばだいたい合っています。セーブポイントのことを「コミット」と呼びます。

**なぜAIオフィスに必要なのか。** 理由は3つです。

1. **AIの仕事ぶりが履歴に残る** — AIは1回の依頼で何十ファイルも作成・編集します。コミットの履歴を見れば「いつ・何を・どう変えたか」が後から全部追えます
2. **壊れても戻せる（保険）** — AIが間違った編集をしても、直前のセーブポイントに巻き戻せます。「AIに大量のファイル操作を任せる」からこそ、この保険が効きます
3. **オフィスごと共有・引き継ぎできる** — 履歴ごと丸ごと人に渡せるので、チーム展開や引き継ぎがしやすくなります

**利用するにはどうすればいいか。**
ここでもコマンドを覚える必要はありません。**git操作はClaude Code自身が全部できる**ので、頼めば導入から日々の記録までやってくれます。唯一の準備は、PCにgit本体が入っていること（入っていなければ、それもClaudeが確認してインストール手順を案内してくれます）。

> **コピペ用プロンプト⑥（git導入）**
>
> ```
> このオフィスのフォルダを git で管理したいです。私は git に詳しくありません。
> 1. この PC で git が使える状態か確認し、必要ならインストールを案内してください
> 2. このフォルダを git リポジトリにして、現在の状態を最初のセーブポイント
>    （コミット）として記録してください
> 3. 今後、私が「コミットして」と言ったら、何を変えたかがわかる日本語の
>    メッセージ付きでセーブポイントを作ってください
> ```

あとは1日の終わりや仕事の区切りに「今日の作業をコミットして」と言うだけです。「先週の状態に戻したい」「昨日何を変えたか教えて」も、そのまま日本語で頼めます。

用語は3つだけ覚えれば十分です: **リポジトリ**（履歴ごと管理されているフォルダ）、**コミット**（セーブポイント）、**コミットログ**（セーブ履歴の一覧）。

### 管理層と保管庫の分離

- **オフィス（git管理）**: ルール・チケット・メモリ・成果物 = 仕事の管理層
- **外部資料庫（別フォルダ）**: 会議資料の正本・取材素材・音声動画 = 資料の保管庫

運用ルールは「資料を探すときはまず保管庫」「正本は動かさない」「必要なテキストだけ案件フォルダにコピー」「重いファイルはパス参照のみ（gitに入れない）」。オフィスが肥大化せず、正本が壊れる事故も防げます。

### スキル（定型業務のマニュアル化）

繰り返す定型業務（例: 取材依頼書の作成、告知メールの生成、規定チェック）は「スキル」として手順書化しておくと、`/コマンド名` 一発で毎回同じ品質の成果物が出ます。**3回以上繰り返した仕事はスキル化を検討する**のが目安です。

## 4. どれで動かすか — Chat・Cowork・Claude Codeの違い

Claudeには主に3つの使い方があり、「AIオフィスが作れるかどうか」がはっきり分かれます。マネする前に、自分がどれを使うかを決めましょう。

| | Chat（claude.ai / アプリのチャット） | Cowork（デスクトップアプリ） | Claude Code |
|---|---|---|---|
| 操作イメージ | ブラウザやアプリでの会話 | PCのフォルダを渡して任せる | ターミナル（黒い画面）での会話 |
| PCのフォルダ・ファイル | 触れない（ファイル添付のみ） | 指定したフォルダ内で読み書きできる | 読み書きに加えコマンド実行まで |
| 記憶の持ち方 | 会話単位（終わると基本リセット） | フォルダ内のファイルに残せる | フォルダ内のファイルに残せる |
| AIオフィス | 作れない | 作れる（基本形は十分動く） | 作れる（フル機能） |
| git・スキル・複数エージェント | ✕ | △（一部は頼めば可能） | ◎（全部入り） |
| 向いている使い方 | 単発の相談・下書き | 非エンジニアの日常業務 | フル活用・自動化したい人 |

### Chat: 相談はできるが、オフィスは作れない

Chatは優秀な「相談相手」ですが、PCのフォルダに触れないため、**このガイドの核である「仕組み側に記憶を持たせる」ことができません**。毎回ファイルを添付し、毎回背景を説明することになります。AIオフィスの代替にはなりませんが、外出先での単発の壁打ち用として併用する分には便利です。

### Cowork: 非エンジニアはここから始めるのがおすすめ

Coworkは、Claudeのデスクトップアプリから**PCのフォルダを指定して仕事を任せられる**機能です。黒い画面は出てきません。フォルダ内のファイルの読み書きができるので、このガイドの基本形——憲法（CLAUDE.md）・チケット・エージェントのメモリ——は**Coworkでもそのまま動きます**。手順章のコピペ用プロンプト①も、Coworkでフォルダを選んでそのまま貼れば使えます。

### Claude Code: フル機能で運用したい人向け

Claude Codeはターミナルで動く分だけ見た目のハードルがありますが、できることは全部入りです。git管理、定型業務のスキル化、複数エージェント（社員）の同時稼働、コマンド実行を伴う自動化まで、このガイドに書いたことがすべて実現できます。

### 使い分けの目安

**まずCoworkでオフィスを開設し、物足りなくなったらClaude Codeに移る**のが、ビジネス職にはいちばん無理のない道筋です。どちらも同じフォルダを開けるので、CoworkからClaude Codeへの移行コストは実質ゼロ。フォルダ（＝オフィス）はそのまま、道具だけ持ち替えられます。

## 5. マネするための手順（最小構成から）

いきなり全部作る必要はありません。以下の順で1週間ずつ試すのがおすすめです。

### 大前提: ファイルは自分で書かなくていい

ここまで読んで「mdファイルをたくさん書くのは面倒だな」と感じた人へ。**自分でmdファイルを書く必要はほぼありません。**

Claude Code はフォルダもファイルも自分で作れます。だから「こういう仕事をしていて、こういうことをAIに手伝ってほしい」とチャットで話せば、**Claudeのほうから質問しながら、憲法もエージェント定義も全部まとめて書いてくれます**。あなたがやるのは次の2つだけです。

1. **話すこと** — 自分の仕事・やってほしいこと・好みを普通の言葉で伝える
2. **確認すること** — できあがったファイルを読んで「ここは違う」と直させる

つまり「AIオフィスを作る作業」自体が、AIへの最初の仕事の依頼になります。以下の各ステップには、そのままClaude Codeのチャットに貼れる**コピペ用プロンプト**を付けました。

### Step 1: フォルダを作り、憲法を書く（初日）

```
my_office/
  CLAUDE.md
  workplace/tickets/{unstarted,in_progress,pending,completed}/
  data/documents/
```

CLAUDE.md には最低限これだけ書けばOK:

1. 自分の役職と業務ドメイン（2〜3行）
2. タスク受領時の動き（チケットを作ってから作業する）
3. 禁止事項（捏造しない・勝手に消さない）

やり方: 空のフォルダを作り、そこでClaude Codeを起動して（Coworkの場合はそのフォルダを作業場所に指定して）、以下を貼るだけです（◯◯◯を自分の言葉に置き換える）。

> **コピペ用プロンプト①（オフィス開設）**
>
> ```
> このフォルダを、私の仕事を手伝ってもらう「AIオフィス」にしたいです。
> 私の仕事: ◯◯◯（役職と主な業務を2〜3行で）
>
> 以下をお願いします。
> 1. 私に質問しながら、このオフィスの憲法となる CLAUDE.md を作成してください。
>    内容は「このオフィスは何の仕事をする場所か」「タスクを受けたらチケットを
>    作ってから作業するルール」「禁止事項（捏造しない・確認なしに消さない・
>    部分完了を完了と報告しない）」を含めてください。
> 2. workplace/tickets/ の下に unstarted / in_progress / pending / completed、
>    それと data/documents/ フォルダを作成してください。
> 3. できあがった CLAUDE.md を私に見せて、直したい点を確認してください。
> ```

Claudeが「あなたの業務で一番多い仕事は?」「報告はどんなスタイルが好みですか?」などと聞いてくるので、答えていけば憲法が完成します。

### Step 2: チケット運用に慣れる（1週目）

Claude Codeに仕事を頼むたび、チケットを作らせて完了時に学びを書かせる。1週間で「自分の仕事の記録がたまっていく感覚」がつかめます。

> **コピペ用プロンプト②（普段の仕事の頼み方）**
>
> ```
> チケットを作ってから、次の仕事に着手してください。
> 完了したらチケットに実施内容・成果物・学びを記録してください。
>
> 依頼内容: ◯◯◯
> ```

### Step 3: 社員を1人ずつ雇う（2週目〜）

**一番よく頼む仕事から1役割だけ**エージェント化します（例: 資料作成が多いなら writer から）。うまく回ったら2人目を追加します。

> **コピペ用プロンプト③（社員の採用）**
>
> ```
> このオフィスに「writer（ライター）」という社員（エージェント）を追加したいです。
> 担当してほしい仕事: ◯◯◯（例: 社内向け資料・メール文面の作成）
>
> 私に質問しながら agents/writer/CLAUDE.md を作成してください。
> 内容は「役割」「行動ルール（文体・品質基準）」「やってはいけないこと」。
> あわせて agents/writer/memory/raw.md を作り、「作業のたびに日付・作業概要・
> 学びを追記する」ルールを CLAUDE.md（憲法）にも書き足してください。
> ```

### Step 4: 判断軸ファイルを育てる（随時）

AIの提案に「自分ならこうしない」と感じた瞬間がチャンスです。その場でこう言えば、Claudeが判断軸ファイルの新設・追記までやってくれます。数週間で「自分の分身度」が体感で上がります。

> **コピペ用プロンプト④（判断軸の記録）**
>
> ```
> いまの提案、私ならこう判断します: ◯◯◯（理由も一言）
> この判断基準を、オフィス直下の「（自分の名前）.md」に追記してください。
> ファイルがなければ「判断の好み」「反省・失敗パターン」の節を持つ形で
> 新規作成し、経営判断系のタスクでは必ず読むよう憲法にも書き足してください。
> ```

### Step 5: 定型業務をスキル化する(1ヶ月目〜)

同じ形式の依頼を3回したら、その手順をスキルにまとめる。ここまで来ると「頼む→数分で定型品質の成果物」の状態になります。

> **コピペ用プロンプト⑤（スキル化）**
>
> ```
> いま作ってもらった◯◯◯、今後も同じ形式で何度も頼む予定です。
> 今回のやり取りをふりかえって、次回から一発で同じ品質のものが出せるように
> スキル（再利用できる手順書）としてまとめてください。
> ```

**ポイント: プロンプトは「丸暗記」しなくていい。** 一度オフィスができれば、憲法にルールが書いてあるので「これやって」だけで回り始めます。上のプロンプトは最初の立ち上げ用の補助輪です。

## 6. 運用のコツ（実運用で分かったこと)

- **AIは相談相手ではなく仕事仲間として扱う。** 「どう思う?」ではなく「チケット作って着手して」と仕事として渡す。ワークフロー自体をAI前提で再設計する
- **記録を義務にする。** 「作業したらメモリとチケットに残す」を憲法に書いておかないと、AIも人間と同じで記録をサボる
- **完璧な設計より運用開始。** フォルダ構成は後から直せる。まず1チケット回すことが先（「評論家ではなく、実践者であれ」）
- **git管理にする。** オフィス全体をgitリポジトリにしておくと、AIの作業履歴がコミットログとして残り、壊れても戻せる（gitが初めての人は3章の補足を参照）
- **固有ルールは適用範囲を明示する。** 例: メディアの表記ルールは記事にだけ適用、経営文書には適用しない、と憲法に書き分ける
- **AIの失敗も資産化する。** ミスが起きたら「なぜ・どうすべきだったか」をメモリや判断軸ファイルに追記する。同じミスが減っていく

---

## 7. この方式で何が変わるか

- **説明コストが消える**: 毎回の背景説明が不要になり、依頼が1〜2行で済む
- **品質が安定する**: 行動ルール・スキル・校閲フローで、成果物のばらつきが減る
- **仕事が資産になる**: チケットの学び・メモリ・判断軸が蓄積し、AIが月単位で「自分専用」に育つ
- **引き継ぎができる**: オフィスごと共有すれば、他の人も同じ仕組みをすぐ再現できる（このガイドのように）

## 付録: 最小テンプレート（コピペ用）

自分で書きたい人向けのテンプレートです。Claudeに作らせた場合も、できあがりがこの骨子を満たしているかの確認用チェックリストとして使えます。

### CLAUDE.md の骨子

```markdown
# CLAUDE.md

## このオフィスについて
（自分の役職と業務ドメインを2〜3行で）

## タスク受領時のルール
1. 担当エージェントを選定する
2. workplace/tickets/ にチケットを作成してから作業を開始する
3. 完了時はチケットに実施内容・成果物・学びを記録する

## エージェント実行ルール
agents/<agent-name>/CLAUDE.md を毎回読んでから作業する。
作業記録を agents/<agent-name>/memory/raw.md に必ず残す。

## ガバナンス（禁止事項）
- データ・成果・報告の捏造
- 確認なしの破壊的操作
- 部分完了を完了済みとして報告すること
```

### チケットの骨子

```markdown
# タスク名

- ID: YYYY-MM-DD_slug
- 優先度: 高/中/低
- ステータス: in_progress
- 担当者: （エージェント名）
- 作成日: YYYY-MM-DD
- 概要: （1〜2行）

## 完了時に記入
- 実施内容:
- 成果物:
- 学び: [INSIGHT] ...
```

### エージェント定義（CLAUDE.md）の骨子

```markdown
# Agent: writer（ライター）

## 役割
（誰のために・何を作る担当か）

## 行動ルール
- （文体・品質基準など3〜5個）

## やってはいけないこと
- （2〜3個）

## メモリ
作業後は memory/raw.md に日付・作業概要・学び（[INSIGHT]付き）を追記する。
```
